# P4.5 对拍：为什么 14 个用例只过 1 个？——都是换行符惹的祸

> 这份笔记讲一桩"怪事"：你的 C++ 代码明明写对了，为什么对拍成绩是 **AC 1 / 14**？
>
> 读完你会明白三件事：
> 
>1. 换行符是什么，为什么 Windows 和 Linux 的换行符不一样；
> 2. 是谁、在哪一步偷偷改了你的输出；
> 3. 为什么把程序交给 WSL 跑，监考老师还坐在 Git Bash 里，问题就好了。

## 1. 故事版：三分钟看懂整件事

把对拍想象成一场**考试**：

| 角色 | 对应东西 | 干什么 |
| :-- | :-- | :-- |
| 考生 | 你的命令行程序（CLI） | 读考卷、写答案 |
| 考卷 | `case*.in` | 一批日志和操作指令 |
| 标准答案 | `case*.ans` | 由一份独立的 Python 朴素实现提前算好 |
| 监考老师 | `run_tests.sh` | 发卷、收答案、和标准答案**逐字比对** |

注意监考老师的比对方式：**一个字节都不能差**。标准答案写 "3"，你交 "3 " 都算错。

怪事就出在"换行"这个动作上。程序每写完一行，就要输出一个**换行符**表示"这行结束了"：

- 在 Linux 的世界里，换行符是**一个字符**，写作 `\n`（n 是英文 newline 的首字母，意思是"新的一行"）；
- 在 Windows 的世界里，换行符传统上是**两个字符**，写作 `\r\n`（多出来的 `\r` 读作"回车"）。

标准答案 `.ans` 是按 Linux 规矩、用 `\n` 存的。
而你在 Windows 上用 g++ 编出来的 `cli.exe`，每次往外写一个 `\n`，
都会被程序自带的"后勤部门"——**C 运行时**（英文缩写 CRT）——**偷偷换成 `\r\n`**。
程序自己对此毫无察觉，它以为自己写的就是 `\n`。

于是监考老师逐字比对时：

```
标准答案： 3 \n
你的答案： 3 \r \n      ← 多了一个 \r，判错
```

14 份考卷里，13 份要写字，全部判错；只有 1 份是**白卷**（0 个操作，标准答案是 0 字节的空文件），
想偷偷改都找不到地方下手——这就是 **AC 1 / 14** 的来历。唯一通过的是 `case13_no_ops`。

那怎么救？`cli_wsl.sh` 的思路简单粗暴：**考生换人**。

让 WSL（Windows 自带的 Linux 虚拟机）里的 Linux 版程序来答卷。
在 Linux 里，`\n` 就是 `\n`，没有任何"后勤部门"会动手脚。
监考老师还坐在 Git Bash 里也没关系——他只负责发卷、收卷、对答案，**从不改答案**。

## 2. 换行符的"前世今生"：为什么会有两种

`\r` 和 `\n` 这两个字符，是从**老式机械打字机**时代继承下来的。

打字机上有个部件叫"字车"，就是装着字模、在纸上来回移动的那个小车。打完一行要做两个动作：

1. **把字车推回最左边**——不然下一个字会打在纸的右边缘外面。这个动作叫"回车"，对应字符 `\r`
   （r 是 return 的首字母，英文全称 carriage return，直译就是"字车回来"）；
2. **把纸往上滚一行**——不然新字会叠在旧字上。这个动作叫"换行"，对应字符 `\n`
   （n 是 line feed 里的 newline，直译"喂一行纸"）。

早期的计算机终端是仿着打字机做的，所以换行需要两个字符 `\r\n`，两个动作各做一次。
后来大家觉得麻烦：

- **Windows** 比较念旧，一直保留 `\r\n` 两个字符的老规矩；
- **Linux（以及后来的 macOS）** 做了简化，换行只用一个 `\n`，"回到行首"这个动作由终端自己脑补。

就这么点历史原因，没有任何高深的道理。但两个系统对"一行怎么结束"的看法不同，
跨系统传递文本时就会闹出我们今天这个 bug。

## 3. 证据：字节不会撒谎

口说无凭，我们把文件拆成**字节**（一个字节就是一个 0~255 的数字，字符在机器里就是这样存的）来看。

常用字符的字节编号（十六进制）：

| 字符 | 字节编号 | 说明 |
| :-- | :--: | :-- |
| `'3'` | `33` | 数字 3 |
| `'2'` | `32` | 数字 2 |
| `\n` | `0a` | Linux 风格换行 |
| `\r` | `0d` | 回车 |

标准答案 `case01_basic.ans` 的开头几个字节是：

```
33 0a 32 0a ...        也就是 "3\n2\n..."
```

Windows 版 `cli.exe` 实际输出的字节是：

```
33 0d 0a 32 0d 0a ...  也就是 "3\r\n2\r\n..."
```

每个 `0a` 前面都被塞了一个 `0d`。内容数字一个没错，**多出来的全是 `0d`**。
这就是"代码对、测试挂"的全部秘密。

## 4. 凶手与作案手法：Windows 的"文本模式"

### 4.1 每个文件都有两种打开方式

在 Windows 上，程序打开一个文件、往里写东西时，有两种模式可选：

- **文本模式**（翻译模式）：好心办坏事的模式。写入时，每个 `\n` 自动变成 `\r\n`；
  读入时，每个 `\r\n` 自动还原成 `\n`。它"贴心"地想帮你统一成 Windows 风格；
- **二进制模式**（不翻译模式）：你写什么就存什么，一个字节都不动。

而 Windows 上程序的标准输入、标准输出（就是 `std::cin`、`std::cout` 接的那两个"流"），
**默认就是文本模式**。所以 `cli.exe` 里这句

```cpp
std::cout << 3 << "\n";
```

程序以为自己写了两个字节 `33 0a`，实际在文本模式下，字节离开进程的前一刻被改成了 `33 0d 0a`。

### 4.2 关键观念：换行符是"流"的属性，不是"文件"的属性

这是本节最重要的一句话，值得停下来想清楚：

> **文件本身（硬盘上那块数据）根本不管你用什么换行。它像个储物柜，你塞什么它就存什么。
> 翻不翻译，只取决于"写字的那个程序"用的是文本模式还是二进制模式。**

证据就在我们的方案里：

- 同一个临时文件，让 Windows 的 `cli.exe` 写，里面是 `\r\n`；
- 同一个临时文件，让 WSL 里的 `./cli` 写，里面是 `\n`。

文件没换、硬盘没换、监考老师没换，**换的只是"谁来写字"**。

### 4.3 监考老师为什么不"睁一只眼闭一只眼"

Git Bash 里的 `diff`（用来比对答案的工具）是 GNU diff，它在 Git Bash 里默认按**二进制模式**读文件：
老老实实按 `\n` 切行，行尾那个 `\r` 会被当成**行内容的一部分**。于是：

```
标准答案的第一行： "3"
你的答案的第一行： "3\r"      ← 字符串不相等，判错
```

顺带一说，Git Bash 里的一整套工具（bash、sed、tr、cat、diff）都有这个特性：
它们尽量模仿 Linux，**从不替你翻译换行符**。这本来是优点（让 Git Bash 像个真的 Linux），
但也意味着这个 `\r` 会被原封不动地揪出来，bug 藏不住。

### 4.4 为什么输入侧从来不惹事

`run_tests.sh` 也会把 `.in` 文件喂给程序。就算输入文件里是 `\r\n` 也没事：

程序用 `std::cin >> s` 读单词，`>>` 是靠"空白字符"来断词的，而 `\r` 和空格、`\n`、制表符一样，
都属于空白字符，会被直接跳过。**输入侧的换行风格基本无害，输出侧才是一刀致命。**
（何况本仓库的 `case*.in` 本来就是 Linux 风格的 `\n`。）

## 5. 解救方案：让 Linux 程序来写字

思路：在 WSL 里用 Linux 的 g++ 编一个 Linux 版程序（名字叫 `cli`，没有 `.exe` 后缀），
再用一个小脚本 `cli_wsl.sh` 当"接线员"，把考试的输入转发给它、把它的答案收回来。

### 5.1 准备工作（在 Git Bash 里，只需做一次，以后改了头文件要重做第 2 步）

```bash
cd /e/cpp-feature/projects/mysol/stage4

# 让 WSL 里的 g++ 把程序编成 Linux 版，产物叫 cli（ELF 格式，Linux 的可执行文件格式）
wsl.exe -e bash -c 'g++ -std=c++17 p4_5_log_analyzer_cli.cpp -o cli'
```

注意：这一步编出来的 `cli` 和你在 Git Bash 里编的 `cli.exe` 是**两个不同的文件**，
一个是 Linux 程序，一个是 Windows 程序，互不覆盖、互不打架。

### 5.2 对拍

```bash
bash ../../tests/stage4/tests/run_tests.sh ./cli_wsl.sh
```

期待最后一行：

```
---------------- AC 14 / 14 ----------------
```

### 5.3 `cli_wsl.sh` 逐行讲解

脚本全文很短：

```bash
#!/usr/bin/env bash
set -u
cd "$(dirname "$0")" || exit 1
exec wsl.exe -e bash -c './cli'
```

逐行看：

**第 1 行 `#!/usr/bin/env bash`**
叫shebang，告诉系统："请用 bash 来解释我。"Git Bash 看到这行就会再启动一个 bash 来跑这个脚本。

**第 2 行 `set -u`**
让 bash 遇到"用了没定义的变量"就报错退出，防止变量名拼错时脚本闷声出错。

**第 3 行 `cd "$(dirname "$0")"`**
- `$0` 是这个脚本自己被调用时的路径；
- `dirname "$0"` 取出它所在的目录；
- 整句意思是"**先进到我脚本所在的目录里**"。

为什么非进不可？因为 `wsl.exe` 启动 Linux 程序时，会把**调用者的当前 Windows 目录**
自动翻译成 Linux 路径（形如 `/mnt/e/...`），当作 Linux 程序的工作目录。
脚本 cd 到 `E:\cpp-feature\projects\mysol\stage4` 之后，WSL 里的程序就正好站在
`/mnt/e/cpp-feature/projects/mysol/stage4` 里，下一行的相对路径 `./cli` 才能找到人。

**第 4 行 `exec wsl.exe -e bash -c './cli'`**
- `wsl.exe`：Windows 与 WSL 虚拟机之间的"大门"；
- `-e bash -c './cli'`：进 Linux 后执行 bash，由 bash 运行当前目录下的 `./cli`；
- `exec`：意思是"我这个壳不活了，直接把我变成 wsl.exe"。好处是少一层进程，
  监考老师拿到的退出码就是 Linux 程序的退出码，"运行时错误"的判定照常工作。

### 5.4 为什么这一路上没人再塞 `\r`

数据的实际旅程是这样的（不用记住名词，记住"谁都不拆包裹"即可）：

```
监考老师（Git Bash）
   │  把 case01.in 的句柄接到输入端，把临时文件的句柄接到输出端
   ▼
cli_wsl.sh（还是 Git Bash 里的 bash，只当接线员）
   │  启动 wsl.exe，两个句柄原样交过去
   ▼
wsl.exe（Windows 和 Linux 虚拟机之间的传声筒）
   │  在虚拟机里搭一个"中转"小进程：一头连 Linux 程序，一头连那两个 Windows 句柄
   ▼
./cli（真正答卷的 Linux 程序）
   写出 "3\n" —— Linux 内核经手，\n 就是 \n
   │
   ▼ 字节沿原路返回
wsl.exe 拿到 "3\n"，用最朴素的方式写进临时文件：给什么写什么，一个字节不添
```

看出来了吗？**这条路上没有任何一个环节使用 Windows 的文本模式**：

- 监考老师和接线员只负责开门、递东西；
- `wsl.exe` 手里虽然攥着 Windows 文件句柄，但它只做"原始搬运"，不理解、也不关心内容是什么；
- 真正写字的是 Linux 程序，走的是 Linux 内核，Linux 压根没有"写 \n 偷偷加 \r"的习惯。

这也反过来印证了第 4.2 节那句话：换行翻译是**写字程序的属性**，不是文件句柄的属性。
写字的人换了，"翻译"就无从发生。

## 6. 路上两个必须知道的坑

### 坑一：Git Bash 会改写以 `/` 开头的参数

Git Bash 在启动**原生 Windows 程序**（比如 `wsl.exe`）时，有个"自作聪明"的习惯：
凡是看起来像 Linux 路径、以 `/` 开头的参数，都会被它自动改写成 Windows 路径。例如：

```
你写的： /mnt/e/某个文件
实际传进去的： Git安装目录/mnt/e/某个文件        ← 凭空拼出来的怪路径
```

然后 WSL 那边就会报"找不到文件"。这个改写**纯粹发生在 Git Bash 这一侧**，
WSL 收到的参数本来是原样的，是 Git Bash 提前动的手。

`cli_wsl.sh` 的对策：**一个以 `/` 开头的参数都不传**。先 `cd` 过去，再用相对路径 `./cli`，
`./cli` 不以 `/` 开头，不会被改写，工作目录则由 `wsl.exe` 自动翻译。

如果你在别的地方绕不开，也可以显式关掉这个改写：

```bash
MSYS_NO_PATHCONV=1 wsl.exe -e bash /mnt/e/某个脚本
```

### 坑二：shell 脚本必须用 LF 换行保存

`cli_wsl.sh` 这个文件本身**必须是 Linux 风格的 LF 换行**。
如果编辑器把它存成了 Windows 的 CRLF，bash 读脚本时会把 `\r` 当成命令的一部分，报这种错：

```
$'\r': command not found
```

记住一个对照：**C++ 源码文件是 CRLF 无所谓，shell 脚本是 CRLF 会直接死。**
VS Code 右下角可以查看和切换文件的换行格式（点一下，选 LF）。

### 坑三（顺带）：改完头文件，要在 WSL 里重新编译

你改的是 `p4_5_log_analyzer.h`，但对拍跑的是 WSL 里的 `cli`。
改完头文件如果忘了重新执行第 5.1 节那条 wsl 编译命令，对拍的还是旧程序，会误以为"改动没效果"。
Git Bash 的 g++ 编的是 `cli.exe`，WSL 的 g++ 编的是 `cli`，别搞混。

## 8. 出问题怎么办

| 症状 | 原因和处理 |
| :-- | :-- |
| 提示 `CLI not found or not executable`（找不到可执行文件） | 给脚本加执行权限：`chmod +x cli_wsl.sh`；并确认命令是在 `projects/mysol/stage4` 目录下跑的 |
| 14 个全是 `[RE]`（运行时错误） | WSL 里的 `cli` 不存在，或者它其实是个 Windows 程序。重跑第 5.1 节的编译命令；还不行就把脚本里的 `exec` 去掉再试 |
| 报 `$'\r': command not found` | 脚本被存成了 CRLF，按坑二改成 LF |
| 报 `No such file or directory`，路径里出现 Git 安装目录 | 撞上了坑一的参数改写，检查是不是传了 `/` 开头的路径 |
| WSL 启动后不在该在的目录，退回了家目录 | 当前 Windows 目录 WSL 挂不上（比如某些网络路径），换到普通盘符目录下调用 |
| 报 `wsl: command not found` | 没装 WSL；装了多个发行版时，先用 `wsl.exe -l -v` 看名字，再用 `wsl.exe -d 名字 -e ...` 指定 |
| 改了头文件但对拍结果纹丝不动 | 忘了在 WSL 里重新编译 `cli`，见坑三 |

## 9. 最后再把整件事复述一遍

1. Windows 的换行是 `\r\n` 两个字符，Linux 的换行是 `\n` 一个字符——打字机时代留下的历史包袱；
2. Windows 程序的标准输出默认是**文本模式**，程序写的每个 `\n`，在离开进程前都被 C 运行时改成 `\r\n`；
3. 监考老师 `run_tests.sh` 逐字节比对，`\r` 藏不住，13 个有输出的用例全挂；零输出的 case13 无从改起，成了独苗；
4. `cli_wsl.sh` 把答题的人换成 WSL 里的 Linux 程序：整条链路上只有人原样搬字节，没有人做翻译，`\n` 原样落盘；
5. 于是成绩从 **AC 1 / 14** 变成 **AC 14 / 14**——而你写的 `p4_5_log_analyzer.h` 自始至终都是对的。
